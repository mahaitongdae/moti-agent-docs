# Security

Security is enforced in code. The system prompt only gives behavioural guidance.

## Controls

| Requirement | Implementation |
|---|---|
| Authentic requests | Teams SDK JWT validation; `microsoft.dangerouslyAllowUnauthenticatedRequests` is refused when `NODE_ENV=production`, and production requires bot credentials. Caddy exposes only `/api/messages` and the Threads tab (`/tabs/threads/*`, `/api/functions/threads.*`, `/api/threads/send`). |
| User identification | Tenant id + Entra object id from the validated activity (`packages/auth/entra/identity.ts`). |
| Tenant allowlist | `microsoft.allowedTenantIds`. Other tenants get no reply; the attempt is audited. |
| User blocking | `UPDATE users SET status = 'blocked' WHERE entra_object_id = '...'`. |
| Session isolation | Personal sessions are keyed and checked by owner; channel sessions belong to the channel thread (`packages/auth/permissions/policy.ts`, `packages/agent/sessions/`). Ownership is re-checked when a queued run starts. |
| Threads tab | Every call, including the streaming send, needs a Teams SSO token validated by the Teams SDK's validator. Only the token holder's own, not hidden, `personal` sessions are listed, shown, answered in, or continued; other users' sessions and shared sessions return the same "not found" and are audited (`packages/agent/threads.ts`). Messages from the tab go through the same limits, queue and tool authorization as chat messages. User text is set as plain text. Answers are rendered from Markdown and sanitized with DOMPurify (no scripts, forms, embedded media or images; links open in a new window). The page's CSP allows scripts, styles and requests only to its own server and images only from itself, so an answer cannot load a remote image to carry data out. The page may be framed only by Teams and Microsoft 365 hosts (`frame-ancestors`). |
| Model access | The default model is for everyone. Other models (`models.extra`) are for members of their Entra groups, checked with the user's own token (`/me/checkMemberGroups`, `User.Read`), cached 10 minutes, and checked again before every answer; on any failure only the default model is allowed (`packages/agent/models.ts`). Channels and group chats always use the default model. Choices are audited (`model_changed`). An optional Pi credential file (`models.authFile`, for a subscription login) is the only file Pi writes besides session files; it sits in a folder only the app can read. Pi runs `!command` values in that file, so only an admin may write it. |
| Per-call authorization | Every tool call is re-validated against its schema and authorized for the actor, session, and arguments before any Graph call (`packages/tools/registry.ts`). |
| Least privilege | Delegated Graph permissions only, no app-only permissions. Microsoft 365 tools only read, except mail changes after approval; nothing deletes mail. Channel threads get only what members can see too: current-channel messages and members, files in the channel's folder, its team's site and the company library, directory names, free/busy times (no subjects), meetings every member is invited to (organizer or attendee, matched by email address), meeting proposals and GitHub tools; group and meeting chats get file reads only from a library everyone in the chat can open (the company library when all members are employees of the tenant and none is a guest; a team's site when all members are in that team's group; checked on every call with `/chats/{id}/members` and `/groups/{id}/members`, cached one minute), the chat's own messages and members (the tools take no chat id, so no other chat can be named), directory names, free/busy times, meetings every member is invited to, a meeting chat's own meeting (subject, time and organizer only), GitHub tools, and skills. `Chat.Read` would let the token read all of the user's chats; only `get_chat_messages` uses it, with the current chat's id. Meeting changes are checked the same way before the card is shown. Mail, OneDrive, other channels and file changes exist only in 1:1 chats. GitHub tools work only for repositories owned by `github.repoOwners` (default `github.project.org`, else the owner of `github.defaultRepo`; `*` turns the check off and leaves only GitHub's own permissions). |
| Approval for changes | The model cannot write. `propose_issue_changes`, `propose_file_changes`, `propose_mail_changes`, `propose_meeting` and `propose_meeting_changes` validate the change with the user's own token and stores it in `pending_actions`. Code applies it only when the same user presses **Apply** on the card, or right away in that user's own 1:1 session when they chose `/mode` **Apply without asking** (`users.change_mode = 'auto'`, audited as `mode_changed`; shared sessions always ask, because other members' messages are in their context); the claim is a single conditional `UPDATE` (owner, `pending`, not expired), so each proposal is claimed at most once. Write requests are not automatically retried on server errors or dropped connections; their outcome may be uncertain and must be checked on GitHub, in OneDrive or SharePoint, or in Outlook before proposing again. File replacements and deletions carry the item's `eTag` (`If-Match`), so a file someone changed after the proposal is not overwritten or deleted. Other users, expired (30 min) or already decided proposals are refused and audited (`packages/agent/proposals.ts`). |
| Scheduled questions | Only in the owner's own 1:1 session: the schedule tools are not offered in channels or group chats, and every read and delete is limited to the owner's rows. A scheduled run uses only the owner's own tokens, posts only to the owner's 1:1 chat, and gets no tools that propose changes, so nothing changes even with `/mode` **Apply without asking**. Blocked users and removed tenants are skipped; limits apply as for any message. The model can create a schedule without a card. Text in a mail or file could ask it to; the harm is limited to read-only answers in the user's own chat and their usage limit (at most 5 schedules per user, `schedule_created` is audited). |
| No shell / filesystem | Pi runs with an explicit tool allowlist; built-in coding tools are never enabled, and the app aborts the run if any unexpected tool appears. Pi's `read` is replaced by the app's own `read`, which reads only files whose real path (links resolved) is inside `skillsDir`; the run aborts unless every active tool is the app's own definition. |
| Secrets | Graph and GitHub tokens stay in the Bot Framework token service and app memory. Secrets come from environment variables; `.env` is git-ignored. Tokens are never put in prompts, transcripts, logs, or audit records. |
| Untrusted content | Tool output is wrapped in `<untrusted_content>` and the model is told to treat it as data. Injected instructions cannot change data on their own: the only write path is a proposal the user must approve (unless they chose **Apply without asking**) on a card that shows the complete preview, including new issue bodies and the full text of every mail to be sent, as plain text. Proposals too large for a card are rejected and must be split. |
| Input validation | Ids are pattern-checked (`driveId:itemId`, GUID team ids, `19:…@thread.*` channel ids) and URL-encoded. Paging links are followed only if they point at the Graph base URL. Content downloads follow Graph's pre-authenticated redirect without sending the user's token. |
| Information leaks | Graph 403 and 404 return the same message. Internal errors are logged, not shown to users or the model. |
| Audit | `tool_invocations` (tool, arguments, status, duration, result size — not content) and `audit_events` (access denied, sessions, sign-in, limits, cancellations, identity mismatch, transcript views, feedback reactions without comment text). |
| Limits | Per-user requests per hour and model cost per calendar month (`usage_records.cost_usd`); global concurrency and queue size; run and tool timeouts. |
| Duplicate deliveries | `inbound_activities` primary key on (tenant, conversation, activity id). |
| Data at rest | Pi transcripts contain conversation content and retrieved excerpts. They live in the `agentdata` volume, created with `umask 077`. Session titles (the first 80 characters of a conversation's first message) are in Postgres. Encrypt the server disk and the backups. |

## Known limits (MVP)

- Prompt injection can still affect what the assistant says, and can make it propose GitHub or mail changes, for example forwarding a mail to an outside address. Those changes still need the user to read the card and press Apply, unless the user turned on **Apply without asking**; then such a change runs at once in their 1:1 chat. The default is to ask.
- Content shared in a channel thread is visible to anyone in that thread, by design.
- Rate limits are per user, not per tenant or team.
- Audit and usage tables have no retention policy yet; prune them according to company policy.
